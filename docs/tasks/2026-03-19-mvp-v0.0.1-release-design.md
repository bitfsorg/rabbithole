# MVP v0.0.1 Release Design

**Date**: 2026-03-19
**Status**: Approved

## Product Definition

BitFS v0.0.1 is a decentralized encrypted file system CLI tool targeting early technical users. Users install from source and can perform encrypted file storage, directory management, content pricing/selling, and paid downloads on BSV testnet/mainnet.

## Target Audience

Early real users who can install from source (`go install` / `go build`). Not a demo — must be stable and usable on mainnet.

## Pre-Release Fixes

### Fix 1: H-1 — acl_ref Semantic Unification

**Problem**: TLV comment says `acl_ref` is "group sig pubkey hash OR ACL rule TxID"; ACL implementation section mandates pubkey-only (permanent node identity, auto-resolves to latest version).

**Fix**: Unify to **pubkey semantics**. Remove "or TxID" from TLV comment. Rationale: pubkey as permanent node identity aligns with Metanet DAG design philosophy; TxID is version-specific and unsuitable for ACL references.

**Scope**: 1-2 documentation edits in `docs/design/bitfs/2-SystemDesign.zh.md`.

### Fix 2: H-2 — Invoice State Persistence

**Problem**: System design promises persistence to `~/.bitfs/invoices/`; actual code is pure in-memory `map[string]*InvoiceRecord`; daemon restart loses all unpaid invoices.

**Fix**: Per-invoice JSON file persistence.

- **Write timing**: On invoice creation and every state change (paid/expired/claimed)
- **Storage format**: `~/.bitfs/invoices/{invoice_id}.json`, one file per invoice
- **Startup recovery**: Scan directory on daemon start, load unexpired invoices into memory map
- **Cleanup**: Eviction deletes disk file alongside memory removal
- **No SIGTERM hook needed**: State is persisted on every mutation

**Not doing**:
- No BoltDB/SQLite (overkill for low invoice volume)
- No on-chain settlement records (out of v0.0.1 scope)

**Scope**: ~200-400 LOC new code in `bitfs/internal/daemon/payment.go` + tests.

### Fix 3: M-1 — Permission Decision Matrix

**Problem**: `acl_ref`, `access` field, and owner fallback have no unified priority rule for conflict scenarios.

**Fix**: Add unified permission decision table to detailed design.

Decision rules:
1. **Write operations**: owner-only (application-layer enforcement, no on-chain constraint in v0.0.1)
2. **Read operations decision chain**:
   - a. Has `acl_ref` → resolve ACL node → decide per ACL rules
   - b. `acl_ref` resolution fails (node missing/corrupted) → **fail-closed**, deny access
   - c. No `acl_ref` → decide by `access` field:
     - FREE → allow
     - PAID → require HTLC payment
     - PRIVATE → require Method 42 handshake (owner or authorized party only)
   - d. No `acl_ref` and no `access` → owner-only

**Not doing**:
- No `share_list` (ACL sufficient for v0.0.1; share_list deferred)
- No covenant on-chain enforcement

**Scope**: Design doc addition + daemon code review for alignment.
