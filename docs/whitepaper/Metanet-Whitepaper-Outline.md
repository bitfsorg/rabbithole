## 摘要

核心主张（一段话概括全文）：

- 去中心化内容分发网络，节点通过**服务数据**（而非证明存储）赚取收入
- BSV 同构侧链，为 BitFS 文件系统提供激励和分发层
- 热数据：自组织市场动力 → payment 检索费吸引更多节点缓存 → 正反馈循环
- 冷数据：一对一存档合约 + ECDH 存储证明（毫秒级，非 zk 证明的数小时 GPU）
- 双币模型：用户用 BSV 付费，MNT 代币仅在运营商间流通
- 结果：随需求扩展、奖励有用工作、无需中心化协调的内容分发网络

## 1. 引言

**问题陈述**：去中心化内容分发尚未解决

**现有系统的不足**：
- IPFS：技术可行但无经济激励 → 数据可用性靠利他主义
- Filecoin：激励面向存储而非检索 → zk 证明耗数小时 GPU → 检索市场被忽视 → 网络优化存档而非分发
- Arweave：一次性付费永久存储 → 无快速检索或地理分布激励
- 传统 CDN（Cloudflare/Akamai）：高效但中心化 → 审查/去平台化/单点故障

**我们的提案**：Metanet 网络 — 反转 Filecoin 模型
- 不是付费让节点存储，而是让节点通过服务数据赚钱
- 核心洞察：如果节点能从交付文件中获利 → 它会选择缓存该文件 → 网络围绕需求自组织 → 类似传统 CDN 但无中心协调
- 不受欢迎的内容 → 存档合约 + ECDH 重加密存储证明（毫秒级替代 zk-SNARK）

**设计哲学一句话**：反转 Filecoin 模型。热数据靠市场激励自组织，冷数据用简单一对一合约，一切运行在 Bitcoin Script 上。

## 2. 与 BitFS 的关系

**定位**：
- Metanet 网络与 BitFS 互补 → 可独立运行
- 类似 IPFS 与 Filecoin 的关系，但设计和范围有重要区别

**职责划分**：
- BitFS = 定义"文件是什么" → 文件系统协议、加密、所有权、访问权转移
- Metanet = 解决"文件存在哪、如何到达用户" → 分发层 + 激励层

**工作流程**：
1. 内容所有者通过 BitFS 发布文件 → 元数据记录在 BSV 链上
2. Metanet 网络分发加密文件内容 → 节点服务请求者 → 收取微支付
3. 所有者无需运行基础设施

**独立性**：
- BitFS 是协议 → 任何服务器都可实现 → 用户可自建 Daemon 直接服务文件
- Metanet 网络面向不想维护服务器的用户 → 去中心化、高可用分发
- 两个独立二进制共享设计理念和密码学原语：`bitfs`（文件系统协议）+ `metanet`（节点运营）。BitFS 使用共享核心库 libbitfs-go；Metanet 目前独立实现，计划未来整合共享库

## 3. 三层架构

```
Layer 1: BSV 主链
  文件所有权(Metanet DAG)、HTLC 购买、payment 下载、元数据永久性
  货币: BSV

Layer 2: 自托管 Daemon
  个人内容服务器(bitfs daemon)、直接文件服务、所有者完全控制
  货币: 无（所有者自有基础设施）

Layer 3: Metanet Chain
  去中心化 CDN、存档合约、支付通道、挖矿奖励
  货币: MNT 代币
```

**各层职责**：
- Layer 1 (BSV)：信任根 → 所有权记录 + HTLC + 元数据 → 永久、抗审查、BSV 全算力保护
- Layer 2 (Daemon)：最简部署 → 所有者完全控制 → 无需代币
- Layer 3 (Metanet Chain)：本文重点 → 协调去中心化 CDN + 管理存档合约 + 处理支付通道

**用户灵活选择**：
- 小型永久文件 → BSV 直接存储
- 所有者控制的大文件 → 自托管 Daemon
- 需要去中心化高可用的 → Metanet 网络
- 可自由组合

**两条链的职责划分**：
- BSV 主链：文件所有权、购买/销售交易、元数据 → 面向终端用户和 AI Agent
- Metanet Chain：存档合约、存储证明、支付通道结算、挖矿奖励 → 面向内容所有者和节点运营商
- 数据无需跨链

## 4. Metanet Chain 设计

**BSV 同构链**：
- "同构" = 结构相同：相同交易格式、Script 引擎、UTXO 模型、密码学原语
- 仅区别：独立创世区块 + 调整的区块参数 + 合并挖矿支持
- 设计选择理由：无需自定义 VM、无新交易类型、无新脚本语言 → 能构建 BSV 交易的工具都能构建 Metanet Chain 交易

**实现路径**：Fork BSV 节点软件 → 替换创世区块 → 调整区块参数 → 添加 AuxPoW 支持

**合并挖矿 (Merge-Mining)**：
- 与 BTC/BSV 矿工共享 SHA-256 PoW
- 矿工在 coinbase 交易中嵌入 Metanet Chain 区块哈希
- 验证条件：父链区块头满足 Metanet Chain 难度 + coinbase 在 Merkle 树中 + 包含正确区块哈希
- 从现有 SHA-256 挖矿生态引导安全性 → 无需专用算力

**防长程攻击 — 锚定**：
- 约每 100 个 Metanet Chain 区块 → BSV OP_RETURN 发布 Merkle 根
- 攻击者重写 Metanet Chain 历史 → 还需重写 BSV 锚定 → 经济上不可行

## 5. MNT 代币经济

**供应计划**：
- 2100 万总供应
- 初始区块奖励 50 MNT
- 每 210,000 区块减半
- 目标出块时间 ~10 分钟

**双币模型**（核心设计特征）：

| | BSV（用户面向） | MNT（运营商面向） |
|---|---|---|
| 角色 | 用户下载付费 | 运营商间交易 |
| 使用场景 | payment 检索费、HTLC 购买 | 存档合约、挖矿奖励、节点间批发 |
| 用户感知 | 用户已持有的货币 | 用户无需知晓 |

**Metanet Node 三种收入来源**：
1. payment 检索费（BSV）— 用户下载内容
2. 存档合约费（MNT）— 内容所有者确保数据可用性
3. 挖矿奖励（MNT）— 出块奖励

**运营商视角**：节点运营商需管理 BSV/MNT 兑换和双资产余额。未来版本将提供自动化兑换工具以降低运营负担。

**MNT 价值逻辑**：
- 内容所有者购买 MNT 支付存档合约
- MNT 需求 = CDN 托管服务需求的函数
- 网络增长 → 更多内容所有者 → MNT 需求增长

## 6. 热数据：自组织 CDN

**核心贡献**：热门内容无需存储合约、无需存储证明、无需协议管理的副本 → 纯市场激励自组织。

**正反馈循环**：
```
热度上升 → payment 收入增加 → 更多节点缓存
    ↑                              ↓
更多用户 ← 更好的可用性 ← 网络中更多副本
```

**冷启动策略**：初始阶段，内容所有者通过自托管 Daemon（Layer 2）直接服务文件。随着 Metanet 节点上线并发现有利可图的内容，它们主动拉取缓存，网络逐步从 Layer 2 自然过渡到 Layer 3。存档合约为初始冷内容提供明确的缓存保障。

**四个显著属性**：
1. 热数据无需存储合约 → 节点自愿缓存因为有利可图
2. 无需存储证明 → BSV 上的 payment 交易记录本身证明节点服务了数据
3. 无需副本管理 → 市场决定正确副本数
4. 无需中心协调 → 每个节点独立做成本效益分析

**节点获取数据的三种渠道**：
1. 内容所有者主动推送
2. 节点从所有者 Daemon 拉取（付 payment 费）
3. 节点间批发购买（MNT 支付通道）

**节点决策逻辑**：预期 payment 收入 > 存储+服务成本 → 缓存。否则不缓存。无需协议强制。

**内容发现**：
- 用户从 BSV 链/Daemon 解析 Metanet 元数据 → 获取 content hash
- 两种定位节点方式：查询 Metanet Chain 存档合约 / 查询覆盖网络查找服务
- 用户按延迟/价格/信誉选择最优节点 → 付 payment 费下载
- 全程去中心化

## 7. 冷数据：存档合约

**适用场景**：个人备份、监管存档、低访问频率数据集 → 检索费不足以吸引自愿缓存

**合约机制**：
- Bitcoin Script 交易（Metanet Chain 上）
- 所有者将 MNT 锁入一系列 UTXO（每个证明周期一个）
- 每周期：节点提交有效存储证明 → 领取该周期付款
- 节点未按时提交 → 所有者可回收锁定代币

**ECDH 存储证明**：
- 向节点分发数据时，用 Method 42 ECDH 密钥派生（详见 BitFS 白皮书 §4）：ECDH(所有者密钥, 节点密钥) 派生的密钥重新加密
- 注：当前实现使用 HMAC-SHA256 模拟 ECDH 共享密钥派生（`shared_secret = HMAC-SHA256(owner_priv, node_pub)`），因 Metanet 独立于 go-sdk。安全属性等效于 ECDH 的对称密钥派生，但不提供 ECDH 的前向保密性。生产版本将迁移至真实 secp256k1 ECDH
- 每个节点持有密码学唯一副本 → 不能互相复制数据满足证明
- Merkle 挑战-响应：challenge = SHA256(contract_txid || period_number) → 确定被挑战的数据块 → 节点返回块数据 + Merkle 证明 → 对照合约中记录的 Merkle 根验证
- 合约 txid 创建前不可预测 → 节点必须保留所有数据块

**副本策略 = 所有者决定**：
- 协议不强制最低副本数
- 3 份副本 → 签 3 个合约
- 地理冗余 → 选不同区域节点

**与 Filecoin 对比表**：

| | Filecoin | Metanet 网络 |
|---|---|---|
| 副本唯一性 | zk-SNARK (PoRep) | ECDH 重加密 |
| 持续验证 | zk-SNARK (PoSt) | Merkle 挑战-响应 |
| 计算成本 | GPU 密集，每扇区数小时 | 毫秒级 ECDH + AES |
| 副本管理 | 协议强制最低数 | 所有者决定（签 N 个合约）|
| 检索激励 | 间接（检索市场存在但非主要激励） | 强（payment 为主要激励）|
| 代币用途 | 存储+检索+质押 | CDN 托管+挖矿（用户付 BSV）|

**安全模型差异**：ECDH 重加密证明与 zk-SNARK 的关键区别在于：ECDH 证明是验证者特定的（verifier-specific），验证者必须持有私钥才能构造挑战；zk-SNARK 证明可公开验证。Metanet 选择 ECDH 因为验证者（合约签订者）已知，且计算效率高出数个数量级。

## 8. 内容收入分成

**收入分配问题**：节点服务文件并收取 payment 费 → 谁拿收入？

**revenue_share 参数**：
- 内容所有者在文件元数据中设置
- 指定节点保留百分比 vs 流回所有者百分比
- 典型 70/30（节点/所有者），完全由所有者决定

**两种合作模式**：
1. 收入分成模式（热门内容）：节点免费缓存和服务 → 赚取检索费分成 → 所有者无需基础设施即可获得被动收入
2. 付费托管模式（冷内容）：所有者通过存档合约付费 → 接受内容不会产生有意义的检索收入

**市场均衡**：
- 分成比例太低 → 无节点缓存
- 分成比例太高 → 所有者放弃不必要的收入
- 市场动态自然决定均衡比例

**节点评估逻辑**：预期检索收入 × 节点分成 > 存储+带宽成本 → 收入分成模式缓存。否则评估存档合约是否覆盖成本。否则拒绝存储。

## 9. 支付通道

**适用场景**：流媒体和大文件传输 → 每KB单独上链支付不现实

**机制**：
- 2-of-2 多签交易锁定资金
- 后续支付 = 签名但未广播的余额更新
- 仅最终结算交易上链 → 数千次微支付压缩为一笔交易

**两种支付通道**：
1. BSV 支付通道：用户↔节点 → 按KB计费的流媒体和大文件下载
2. MNT 支付通道：所有者↔节点（持续存档付款）+ 节点↔节点（批发数据购买）

**payment 通道扩展**：
- 客户端声明通道支付支持
- 服务器返回通道定价（可能低于单次定价）
- 后续请求包含签名余额更新 → 无需链上确认

**争议解决**：
- 递增序列号
- 双方交换旧状态撤销密钥
- 广播过期状态 → 对方可在窗口期内提交惩罚交易 → 没收全部通道余额
- OP_CHECKSEQUENCEVERIFY 时间锁保障（脚本生成部分实现中）

**支持的用例**：
- 按秒计费的流媒体
- 按KB计费的大文件下载（中断可恢复）
- 长期订阅（周期性通道付款）

## 10. 与现有系统对比

| | Metanet 网络 | Filecoin | IPFS | Arweave | 传统 CDN |
|---|---|---|---|---|---|
| 主要激励 | 检索(payment) | 存储(PoSt) | 无 | 一次性存储费 | 服务合同 |
| 副本模型 | 自组织(市场) | 协议强制最低 | 无(利他 pin) | 捐赠基金 | 中心化管理 |
| 存储证明 | ECDH+Merkle(ms) | zk-SNARK(GPU数小时) | 无 | SPoRA(中等) | 无(信任) |
| 原生货币 | MNT(运营商)+BSV(用户) | FIL | 无 | AR | 法币 |
| 用户付费 | BSV(payment 微支付) | FIL | 免费 | 上传后免费 | 订阅/带宽 |
| 区块链 | BSV 同构侧链 | 自定义(Lotus) | 无 | 自定义 | 无 |
| 内容加密 | 默认(Method 42) | 可选 | 无 | 无 | 仅 TLS(传输层) |
| 数据交易 | HTLC 原子交换 | 无原生 | 无 | 无 | DRM/付费墙 |
| 地理分布 | 市场驱动(利润) | 无激励 | 无激励 | 无激励 | 中心化优化 |
| 冷数据策略 | 一对一存档合约 | 扇区交易 | Pin 服务 | 设计即永久 | 源站服务器 |

**根本区别**：Filecoin 付费让节点证明存储，Metanet 让节点通过服务数据赚钱 → 不同激励方向产生不同网络行为（Filecoin 优化持久性，Metanet 优化可用性和交付性能）。

**两个额外差异化点**：
1. BSV 同构链 → 无新密码学原语、无自定义 VM、无新脚本语言
2. 双币模型 → 终端用户完全与 CDN 内部经济隔离 → 用户付 BSV 得数据，无需知道 Metanet Chain/MNT 的存在 → 主流采用的关键

## 11. metanet CLI

**最小命令集**：
```
metanet init          初始化新节点（生成密钥、配置存储）
metanet start         启动节点守护进程
metanet stop          优雅关闭
metanet status        节点状态：运行时间、对等节点、缓存文件、收入、合约

metanet contracts     活跃存档合约、存储用量、证明计划
metanet peers         连接的对等节点、网络拓扑、带宽统计
metanet mine          启用/配置合并挖矿
```

**Metanet Node 本质**：运行在提供者模式的 BitFS daemon → HTTP 服务加密内容 + 处理 payment 支付 + 维护存档合约 + 提交存储证明 + 可选合并挖矿

**运营商两个关键决策**：
1. 缓存什么内容（基于预期检索收入）
2. 接受多少存档合约（基于可用存储容量和 MNT 定价）

**低准入门槛**：
- 有存储、带宽和 BSV 钱包的任何机器都可参与
- 无最低质押、无罚没机制、无复杂设置
- 下载软件 → 初始化 → 开始缓存有利可图的内容
- 网络有机增长

## 12. 结论

总结要点：
- 检索激励弥补去中心化存储生态的空白
- payment 正反馈循环 → 热门内容自组织高可用分发
- 存档合约 + ECDH 存储证明 → 冷数据保障（计算开销降低数个数量级）
- 双币模型 → 用户用 BSV、运营商用 MNT → 主流采用无摩擦
- 与 BitFS 合力 → 完整的去中心化内容平台：数据由创建者所有、默认加密、无信任原子交换交易、经济激励节点分发
- 技术选择刻意保守：BSV 同构侧链 / Bitcoin Script / ECDH+Merkle / 合并挖矿 → 降低复杂性、构建在成熟基础设施上、降低参与门槛
- 贡献不在组件而在组装方式：协议奖励正确行为，网络从个体经济决策中涌现
