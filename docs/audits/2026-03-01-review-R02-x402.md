## Findings

### CRITICAL

无。

HTLC 构建、capsule hash 绑定、replay 保护机制正确。

### HIGH

**H-1: `VerifyPayment` 不验证交易签名 — 支付伪造风险**

`verify.go` L15-98: 反序列化交易后只检查输出是否有正确地址和金额，但从不验证输入签名。攻击者可构造输出正确但输入完全伪造的交易通过验证。

缓解因素：daemon 层应独立广播并确认交易上链。但 `VerifyPayment` 作为独立库函数给出了虚假的安全感。

**建议**:
- (a) 添加签名验证（使用 go-sdk script interpreter），或
- (b) 重命名为 `CheckPaymentOutputs` 并显著文档化此函数不验证签名，调用者必须独立确认交易被网络接受：
  ```go
  // WARNING: This function does NOT verify input signatures. Callers must
  // independently confirm the transaction is accepted by the network (mempool
  // or confirmed) before delivering content.
  ```

**H-2: `VerifyPayment` 不绑定 Invoice ID — 跨 invoice 支付重用**

`verify.go` L15-98: 验证时完全忽略 `Invoice.ID`。对同一 seller、相同地址、相同或更高金额的交易，Invoice A 的支付证明也能通过 Invoice B 的验证。

HTLC 路径有 InvoiceID 嵌入脚本的 replay 保护，但简单 P2PKH 支付路径没有。若 seller 跨 invoice 复用地址，buyer 可一次支付多次使用。

**建议**: daemon 层的 `usedTxIDs` 已存在（确认已实现）。`VerifyPayment` 应显式文档化此限制，理想情况下返回 TxID 供调用者追踪。

### MEDIUM

**M-1: `generateInvoiceID` 在 `rand.Read` 失败时降级到时间戳**

`invoice.go` L80-87: CSPRNG 失败时回退到 `time.Now().UnixNano()`。在支付系统中无法获取随机数时静默降级是危险的。

**建议**: CSPRNG 失败应 panic 或返回 error。支付系统不应在无工作 CSPRNG 的情况下运行。

**M-2: `SetPaymentHeaders` 不验证 nil headers 参数**

`headers.go` L29-36: nil `*PaymentHeaders` 会导致 nil pointer panic，可能导致运行中的 daemon 崩溃。

**建议**: 入口处添加 nil 检查。

**M-3: `CalculatePrice` 溢出时返回 `MaxUint64` 无错误信号**

`invoice.go` L36-50: 溢出时返回 `math.MaxUint64` satoshis（约 1.8×10¹¹ BTC）。下游代码若直接使用此价格会尝试收取不可能的金额。

**建议**: 返回 `(uint64, error)` 明确信号溢出，或文档化 `MaxUint64` 为哨兵值。

**M-4: `BuildHTLCFundingTx` 费用估算使用固定 148 字节/输入**

`htlc_tx.go` L198: 固定 148 字节估算可能低于实际大小，且当无找零输出时估算仍包含 `changeOutputSize`，导致实际费用偏高。

**建议**: 仅在会创建找零输出时包含 `changeOutputSize`。

**M-5: `BuildBuyerRefundTx` 信任 `FundingAmount` 无交叉校验**

`htlc_tx.go` L491-571: 错误的 `FundingAmount` 会导致签名无效但无错误提示。

**建议**: 添加文档说明 `FundingAmount` 必须精确匹配 HTLC 输出金额。

### LOW

**L-1: `VerifyPayment` 手动字节比较**: `verify.go` L67-78 应使用 `bytes.Equal()`。

**L-2: `Invoice.KeyHash` 不由 `NewInvoice` 填充**: 需调用者手动设置。建议添加参数或文档化。

**L-3: 测试辅助函数重复**: `validHTLCParams()` 和 `makeHTLCParams()` 功能相同。

**L-4: 部分函数覆盖率 < 80%**: `BuildHTLC` 69.5%、`ExtractCapsuleHashFromHTLC` 64.3%，但未覆盖路径为 go-sdk 调用的错误分支，可接受。

### SUGGESTIONS

**S-1.** 添加端到端 Script 解释器测试 — 验证 HTLC 锁定/解锁脚本对在 Bitcoin Script 中正确求值为 true。

**S-2.** 为 `VerifyPayment` 添加 `time.Time` 参数（或 clock 接口），避免 `time.Now()` 导致的时间敏感测试。

**S-3.** 考虑统一的 `VerifyHTLCClaim` 函数，整合链上确认 + claim tx 验证 + capsule 提取。

## Summary

x402 是一个工程质量优秀的 HTLC 支付协议实现。spec 一致性 100%，之前的 P0 安全问题已全部修复。

最显著的发现是 H-1（`VerifyPayment` 不验证签名）和 H-2（简单支付路径无 invoice 绑定）。H-1 被 daemon 层的链上确认缓解，H-2 被 daemon 层的 `usedTxIDs` 缓解，但库函数层面的保护不足值得改进。MEDIUM 发现中 M-1（CSPRNG 失败降级）最值得关注 — 支付系统不应在无随机数源时继续运行。

HTLC 脚本构建、capsule hash 计算、签名生成和预签名退款机制的密码学核心健全。
