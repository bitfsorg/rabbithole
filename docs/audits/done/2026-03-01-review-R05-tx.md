## Findings

### CRITICAL

无。

### HIGH

**H-1: `EstimateFee` 大输入时整数溢出 — 潜在费用计算错误**

`opreturn.go` L208: `uint64(txSizeBytes) * feeRate` 可在大载荷和高费率时溢出 uint64。溢出回绕到小值导致严重欠费（交易卡住），或回绕到过大值导致 `ErrInsufficientFunds` 拒绝服务。

当前实际风险低（BSV 费率 1 sat/KB，载荷 KB 级），但构造不安全。

**建议**: 添加溢出检测，饱和到 `math.MaxUint64`。

**H-2: `BuildDataTransaction` 是一个 stub — 实际不构建交易**

`metanet_tx.go` L27-73: 文档描述 "Template 4 — OP_DROP content"，但函数体从不创建 Transaction 对象，不构建 OP_DROP 脚本，返回 `RawTx: nil`。测试只检查 `NodeUTXO != nil`，未验证 `RawTx`。

**建议**: 完成实现或移除公共 API，改为返回 `errors.New("not yet implemented")`。

**H-3: Fee 输入 UTXO 可能与 node 输入 UTXO 重叠 — 潜在 double-spend**

`batch.go` L226-237: `Build()` 对 node 输入去重，但从不检查 fee 输入是否与 node 输入重复。相同 UTXO 同时作为 node 输入和 fee 输入会产生无效的 double-spend 交易。

且 fee 输入自身也不去重。`totalAvailable` 会重复计入金额，掩盖 `ErrInsufficientFunds`。

**建议**: 扩展 `addedInputs` map 覆盖 fee 输入。

### MEDIUM

**M-1: `ParseTxNodeOps` 不处理 OpDelete 输出格式**

`opreturn.go` L125-166: 无条件要求每个 Metanet OP_RETURN 后跟 P2PKH 输出，但 `Build()` 产生的 OpDelete 只有 OP_RETURN 无 P2PKH。解析自己构建的交易会报错。

**建议**: 检查下一个输出是否为 P2PKH，非 P2PKH 时当作 delete 处理。

**M-2: `Build()` 静默接受 OpUpdate/OpDelete 的 nil InputUTXO**

`batch.go` L106-121: OpUpdate 语义上*必须*花费现有 UTXO（更新节点），但 nil InputUTXO 通过验证。OpDelete 的 nil InputUTXO 同样无语义意义。

**建议**: 按 op 类型验证 InputUTXO 必要性。

**M-3: `EstimateTxSize` 公式对多 op batch 不正确**

`opreturn.go` L215-228: 只计算一个 OP_RETURN 开销，但 3-op batch 有 3 个独立的 OP_RETURN 输出。低估约 150 字节/额外 op。BSV 1 sat/KB 费率下实际影响小（几 sat），但公式结构错误。

**建议**: 接受 `numOPs` 参数，按实际 OP_RETURN 数量计算开销。

**M-4: Change 输出 fallback 发送到第一个 op 的 node key**

`batch.go` L301-307: 未设置 `changeAddr` 时回退到 `b.ops[0].PubKey`（node key）。Node key 是每文件/目录的，不是钱包 key。对 OpDelete 的第一个 op，节点正在销毁。

**建议**: 无 changeAddr 时返回错误而非静默选择 fallback。

**M-5: `Sign()` 使用 `InputUTXO.PrivateKey`，但 `Build()` 验证 `op.PrivateKey`**

`batch.go` L329-382: 签名密钥来自 `op.InputUTXO.PrivateKey`，但构建阶段验证 `op.PrivateKey`。两个 PrivateKey 字段冗余且可不一致。调用者可设置 `op.PrivateKey = someKey`（通过验证）但 `op.InputUTXO.PrivateKey = nil`（签名失败）。

**建议**: 消除冗余，只使用 `InputUTXO.PrivateKey`。

**M-6: `MetaFlagBytes` 是可变的包级 `var`**

`opreturn.go` L13-15: `[]byte` 不能是 `const`，但任何代码可修改 `MetaFlagBytes[0] = 0xff`，破坏所有后续 OP_RETURN 解析。并发修改可能 data race。

**建议**: 改为返回副本的函数，或使用 `[4]byte` 固定数组。

### LOW

**L-1: `testFeeUTXO` 辅助函数缺少 ScriptPubKey 和 PrivateKey**: 鼓励不完整测试。

**L-2: `ParseTxNodeOps` 静默跳过畸形 OP_RETURN**: 跳过逻辑可能导致后续 op 的输出索引错位。

**L-3: 无载荷大小上限**: `Build()` 接受任意大载荷。应添加合理上限（如 100KB/op, 1MB/batch）。

**L-4: `BatchNodeResult.NodeVout` 对 OpDelete 为 0**: 与合法 vout 0 不可区分。建议使用哨兵值或 `IsDelete` 字段。

**L-5: `ChangeUTXO.ScriptPubKey` 未填充**: 后续交易需要 ScriptPubKey 计算 sighash。Node UTXO 有填充。

**L-6: 无 OpDelete 在输出中间位置的 ParseTxNodeOps 测试**: 仅测试了 OP_RETURN 在末尾的情况。

### SUGGESTIONS

**S-1.** `Build()` 后使 `MutationBatch` 不可变 — 添加 `built` 标志防止后续 `Add*`。

**S-2.** 三次去重迭代可合并为单次遍历。

**S-3.** 提取 `(BatchNodeOp).Validate()` 方法，允许添加前验证。

## Code Quality Assessment

**优点**:
- Build/Sign 两阶段设计，签名前可审查
- UTXO 去重正确处理"父 UTXO 被子创建和父更新共享"模式
- 3 个 fuzz target（OP_RETURN 解析 + 费用估算）
- 88.9% 覆盖率，88 个测试，`-race` 通过
- Sentinel error 一致使用

**不足**:
- `BuildDataTransaction` 死代码伪装为工作函数
- 双 PrivateKey 字段混乱
- Fee 估算公式结构性错误
- 无载荷大小上限
- Change fallback 危险

## Summary

tx 包是 BitFS 唯一的链上交易构建路径。MutationBatch 架构健全，UTXO 去重正确，测试覆盖强。

**应在主网使用前修复**:
- H-2: `BuildDataTransaction` stub — 移除或完成
- H-3: Fee 输入与 node 输入可重叠（无效交易）
- M-1: `ParseTxNodeOps` 不能解析自己构建的 OpDelete 交易

**重要但非阻塞**:
- H-1: EstimateFee 溢出（当前低风险但构造不安全）
- M-2~M-6: 验证缺口、公式错误、冗余字段、可变协议常量

关键安全属性正确：输出确定性布局、OP_RETURN 从类型化字段构建（无注入）、签名与构建分离。问题在边缘 — stub 代码、不常见 op 类型的验证缺失、公式不准确。在当前 vault 层提供正确输入的使用模式下无资金损失风险。
