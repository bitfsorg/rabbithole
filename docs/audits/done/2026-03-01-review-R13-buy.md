## Findings

### CRITICAL

**C-1: InvoiceID 不匹配 — 所有付费内容购买交易必然失败**

**根因链条**:

1. Daemon `payment.go` L200-213 构建 HTLC 时包含 `InvoiceID: invoiceIDBytes`（16 字节随机 nonce），存储为 `invoice.HTLCScript`
2. Daemon `payment.go` L230 在 `/_bitfs/buy/{txid}` 响应中包含 `"invoice_id": invoice.ID`
3. `client/client.go` L61-67 的 `BuyInfo` 结构体**无 `InvoiceID` 字段** — JSON 反序列化时 `invoice_id` 被静默丢弃
4. `buy.go` L89-99 的 `BuildHTLCFundingTx` 调用**未传入 InvoiceID**（`HTLCFundingParams.InvoiceID` 为零值 nil）
5. 买方 HTLC 脚本不含 InvoiceID 前缀，卖方 HTLC 脚本包含
6. `handleSubmitHTLC` L300 调用 `x402.VerifyHTLCFunding(htlcBody, invoice.HTLCScript, ...)` — 逐字节比较（`htlc_tx.go` L113: `bytes.Equal`）
7. 脚本不匹配 → 返回 `ErrNoMatchingOutput` → **每次购买都失败**

`x402.HTLCFundingParams` 已有 `InvoiceID` 字段（`htlc_tx.go` L35），仅需在 `BuyInfo` 中添加字段并传递。

**修复**: (1) `BuyInfo` 添加 `InvoiceID string \`json:"invoice_id"\``，(2) `buy.go` L89 传入 `InvoiceID: invoiceIDBytes`。两行修改。

### HIGH

**H-1: 付款后未验证 capsule hash**

`buy.go` L104-122: `SubmitHTLC` 返回 capsule 后，代码解码 hex 但**从不验证 `SHA256(capsule) == capsuleHash`**。`capsuleHash` 在 L62 已解码可用。恶意 daemon 可返回伪造 capsule，买方已付款但获得无法解密的数据。

**建议**: 添加 `if !bytes.Equal(sha256(capsule), capsuleHash) { return error }`。

**H-2: 手续费估算假设 P2PKH 输出 — HTLC 输出被低估**

`utxo.go` L19-24: `EstimateFee` 注释和实现明确为 "standard P2PKH transaction"，每个输出 34 字节。HTLC 输出脚本（含 hash lock + time lock + optional InvoiceID prefix）约 143-161 字节，远大于 34 字节。系统性低估手续费可能导致交易被节点拒绝。

**建议**: 为 HTLC 交易提供专用的手续费估算函数。

**H-3: `BuyParams.Client` nil 时 panic**

`buy.go` L47: `Validate()` 检查 `p.Client == nil` 返回错误，但 `Buy()` 函数入口（L54）在 `Validate()` 之前直接调用 `params.Client.GetBuyInfo()`。实际上 L54 处的代码路径是 `err := params.Validate()`，验证在先。但检查测试发现一些测试路径绕过了 Validate。

**修正**: 经验证，`Buy()` L54 首先调用 `params.Validate()`，nil panic 仅在直接调用内部函数时触发。降级为 LOW。

### MEDIUM

**M-1: `price + fee` uint64 溢出无检查**

`buy.go` L156 和 `utxo.go` L67: `price+fee` 为无保护的 uint64 加法。若两者之和超过 2^64 则静默回绕为小值，可能通过 "余额充足" 检查。实际 BSV 值域下极不可能触发。

**M-2: `CostSatoshis` 死代码**

`buy.go` L130-134:
```go
cost := totalInput // Conservative: total spent from wallet
if fundingResult.HTLCAmount < totalInput {
    cost = totalInput  // 与上一行完全相同
}
```
if 分支无论是否执行，`cost` 始终等于 `totalInput`。整个条件块为死代码。

**M-3: 网络设置不可覆盖**

`config.go`: `LoadConfig` 从配置文件加载网络设置，但无 CLI flag 或环境变量覆盖机制。用户无法在不修改配置文件的情况下切换网络。

**M-4: `buyInfo.CapsuleNonce` 静默忽略**

`buy.go`: `BuyInfo.CapsuleNonce` 在响应中接收但 `Buy()` 函数不使用此值。nonce 对买方解密必要（buyer_mask 计算），但传递到 `BuyResult` 后续是否使用取决于调用者。应文档化。

### LOW

**L-1: `os.UserHomeDir()` 错误被吞没**: `config.go` — 配置文件路径解析失败时静默使用空路径。

**L-2: 全零密钥被接受**: `buy.go` — `Validate()` 不检查全零 private key。

**L-3: 零金额 UTXO 被接受**: `utxo.go` — `SelectUTXOs` 不过滤 `Amount == 0` 的 UTXO。

**L-4: `HandleError` 双重错误类型检查**: `exit.go` — 同时检查 `errors.Is` 和类型断言，冗余。

**L-5: 静默配置 key 拼写错误**: `config.go` — 未知配置键不报错。

### SUGGESTIONS

**S-1.** 添加 `context.Context` 参数到 `Buy()` — 支持超时和取消。

**S-2.** `EstimateFee` 应接受输出脚本大小参数，而非硬编码 34。

## Summary

buy 包是买方支付流程的核心，结构清晰但有 **1 个 CRITICAL** 级别 bug：InvoiceID 不匹配导致所有 HTLC 付费购买必然失败。这是 P0 安全修复（InvoiceID 绑定）的不完整实施 — 修复了服务端（daemon 构建带 InvoiceID 的 HTLC）但遗漏了客户端（BuyInfo 未传递 InvoiceID、Buy 未使用 InvoiceID）。修复只需两行代码。

**必须修复**:
- C-1: InvoiceID 传递断裂 — 两行修复
- H-1: capsule hash 验证缺失
- H-2: HTLC 手续费低估
