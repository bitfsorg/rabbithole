## 发现（按严重级别）

### H-1 `acl_ref` 标识语义冲突，导致权限锚点边界不一致

- 证据 A：`acl_ref` 在 TLV 注释中描述为“群签名公钥哈希或 ACL 规则 TxID”
  - `docs/design/bitfs/2-SystemDesign.zh.md:357`
- 证据 B：ACL 章节又明确 `acl_ref` 指向 ACL 节点 `pubkey`（非 txid），并自动解析到最新版本
  - `docs/design/bitfs/2-SystemDesign.zh.md:2336`
  - `docs/design/bitfs/2-SystemDesign.zh.md:2355`
- 风险：实现方可能采用不同 ID 语义（txid / pubkey / hash），导致权限检查、回溯审计、版本更新行为不一致。

### H-2 下载计费状态持久化与支付接口描述冲突，影响“可追溯结算”边界

- 证据 A：系统设计声明发票状态默认持久化到 `BITFS_HOME/invoices`，重启可恢复
  - `docs/design/bitfs/2-SystemDesign.zh.md:1705`
- 证据 B：详细设计仍写“Created 存入 `Server.invoices map`”
  - `docs/design/bitfs/3-DetailedDesign.zh.md:1979`
- 证据 C：详细设计 `POST /_bitfs/pay/{invoice_id}` 仍标注“当前版本接受空 body”
  - `docs/design/bitfs/3-DetailedDesign.zh.md:1754`
- 对照基线：顶层边界要求支付结算状态不可长期仅链下不可追溯
  - `docs/design/OverallDesign.zh.md:69`
- 风险：结算恢复语义与接口安全语义可能被不同实现解释，出现“文档一致但行为不一致”。

### M-1 权限判定链路缺少统一决策矩阵（`access` / `acl_ref` / `share_list` / owner fallback）

- 证据 A：概念设计强调“链上权限记录（access 字段）”
  - `docs/design/bitfs/1-ConceptDesign.zh.md:58`
- 证据 B：详细设计定义优先级 `acl_ref > share_list > 默认 owner 权限`
  - `docs/design/bitfs/3-DetailedDesign.zh.md:3141`
- 证据 C：系统设计定义 `w` 为应用层强制，并定义无 `acl_ref` 时 owner fallback
  - `docs/design/bitfs/2-SystemDesign.zh.md:2252`
  - `docs/design/bitfs/2-SystemDesign.zh.md:2541`
- 风险：缺少“最终授权判定表”时，不同模块可能在冲突输入下给出不同授权结果。

## 决策记录（会话内新增）

### D-2026-03-05-01 应用专用语义不进入底层核心字段

- 决策：BitFS 作为底层文件系统，核心 TLV 字段应保持通用文件系统语义；不应为单一上层应用（如 Git）在核心层引入专用字段。
- 适用范围：后续新增字段评审（NodeType、TLV Tag、核心 payload 字段）。
- 判定标准：
  1. 是否对所有应用通用；
  2. 没有该字段底层文件系统是否无法工作；
  3. 是否必须由底层统一链上验证而不能由应用扩展层承载。
- 结论约束：若不满足以上标准，归入扩展层设计，不进入核心协议字段集合。

### D-2026-03-05-02 BitFS 实现基线对齐 US20210399898A1

- 决策：BitFS 的总体方法学以专利文档 `0-US20210399898A1-STORING DATA ON A BLOCKCHAIN.pdf` 为实现基线，设计评审与详细方案优先参照该专利中的方法展开。
- 适用范围：概念设计、系统设计、详细设计、交易模板族评审、权限/支付/数据上链方案比较。
- 约束说明：
  1. 新方案评估时，默认先给出与专利方法的一致性映射；
  2. 若偏离专利方法，需明确偏离原因、收益与风险；
  3. 在不破坏既有边界原则前提下，优先选择与专利方法更一致的实现路径。

### R-2026-03-05-01 `content` 与 `FILE/DIR/LINK` 去重

- 角色：
  - 外部审查者（User）：提出“`content` 是否与文件/目录重复”
  - 协作审查者（Assistant）：给出分层模型并完成语义收敛
- 讨论结果：
  - `content` 不作为独立节点类型。
  - 节点命名层只保留 `DIR | FILE | LINK`。
  - 数据层（内容对象）只属于 `FILE` 的某个版本（可称 `blob`/`file_data`）。

### R-2026-03-05-02 `LINK` 目标字段统一建模

- 角色：
  - 外部审查者（User）：提出 `link target` 二分（最新头/固定版本）并推动命名收敛
  - 协作审查者（Assistant）：提供字段约束与编码建议
- 讨论结果：
  - `link_target_type` 取值采用：`target_head`、`target_version`。
  - 目标字段收敛为单一 `link_target`（不再拆分 `target_node/target_txid/target_vout`）。
  - 解析规则：
    - `target_head`：`link_target = NodeID`
    - `target_version`：`link_target = txid:vout`（outpoint）
  - 保留 `link_target_type`，避免仅靠字符串内容推断类型造成歧义。

### R-2026-03-05-03 `canonical` 与 txid/vout 编码约束

- 角色：
  - 外部审查者（User）：追问 canonical 含义与 BSV 标准格式
  - 协作审查者（Assistant）：定义规范化输入/存储边界
- 讨论结果：
  - `canonical` = 入链前统一成唯一、无歧义表示。
  - 外部可接受 path/paymail/pubkey/txid 等输入，但链上只存规范化结果。
  - `target_txid`（若拆分表达时）遵循 BSV 通用展示格式：64 hex、无 `0x`。
  - `target_vout` 使用非负整数（建议 `uint32`）。

### R-2026-03-05-04 父子关系与移动语义（HD 派生约束）

- 角色：
  - 外部审查者（User）：明确“子节点密钥由父节点派生，跨父目录不应保持同一节点身份”
  - 协作审查者（Assistant）：将其固化为树模型与操作语义
- 讨论结果：
  - `FILE/DIR` 结构按“单父”约束建模为树（非多父 DAG）。
  - 跨父目录移动时，节点身份（NodeID）必须变化。
  - 跨父目录 `MOVE` 语义：`Create(new parent, new node)` + `Delete(old node)`。
  - 同父目录 `rename` 可保持 NodeID 不变（仅目录项名称变化）。
  - `parent` 字段是否保留为链上冗余字段：待后续字段审查最终拍板。

### R-2026-03-05-06 `index` 字段（HD 派生定位）

- 角色：
  - 外部审查者（User）：确认 `index` 方案
  - 协作审查者（Assistant）：提出约束与迁移语义
- 讨论结果：

### R-2026-03-05-07 `child_entry` 的 `name` 归属与 `index` 去重

- 角色：
  - 外部审查者（User）：追问 `name` 放置位置与 `index` 是否父子双写
  - 协作审查者（Assistant）：给出“单一真相”约束建议
- 讨论结果（已确认）：

### R-2026-03-05-08 `child_entry.child_node` 标识语义

- 角色：
  - 外部审查者（User）：询问 `child_node` 是否应为公钥或 txid
  - 协作审查者（Assistant）：给出节点标识与版本标识分层建议
- 讨论结果：
  - `child_entry.child_node` 应表示“节点身份”（NodeID），不表示“版本”。
  - 因此不使用 `txid`（`txid` 是版本/交易标识，属于 `target_version` 语义）。
  - 当前实现语义下，NodeID 采用 `P_node`（压缩公钥 33B）作为链上编码。

### R-2026-03-05-09 `next_child_index` 连续性（seed 恢复约束）

- 角色：
  - 外部审查者（User）：指出“不应跳号”，以避免 seed 恢复依赖 gap 扫描
  - 协作审查者（Assistant）：将分配规则收敛为严格连续模型
- 讨论结果（已确认）：
  - `next_child_index` 保留，且采用严格连续分配，不允许跳号。
  - 新建子节点时分配 `index = next_child_index`，成功后 `next_child_index += 1`。
  - 删除节点不回收旧 `index`，但不会产生“分配序列跳号”。
  - seed 恢复可按 `0..next_child_index-1` 顺序派生，不依赖 gap limit 扫描策略。

### R-2026-03-05-10 `acl_ref` 字段功能定位（权限策略锚点）

- 角色：
  - 外部审查者（User）：要求详细解释 `acl_ref` 的实际功能
  - 协作审查者（Assistant）：给出职责边界与判权流程说明
- 讨论结果（已确认）：
  - `acl_ref` 的核心功能是“把数据节点与权限策略解耦”：
    - 数据节点负责内容与元信息；
    - ACL 节点负责“谁可读/谁可写”的规则。
  - `acl_ref` 本身不承载权限规则，只是指针（引用）。
  - `acl_ref` 推荐统一语义为 ACL NodeID（`P_node`），解析到 ACL 节点最新版本。
  - 判权流程：
    1. 读取目标节点元信息；
    2. 若有 `acl_ref`，解析 ACL 节点并执行权限判定；
    3. 若无 `acl_ref`，回退到默认规则（`access`/owner）；
    4. 与支付字段（定价/发票）分离，不在 `acl_ref` 中混合结算语义。
  - 一个 ACL 节点可被多个文件/目录共享引用，便于集中改权限（改一次，多处生效）。

    - 当前 DataTx 锁定目标是 `P_node`（节点身份地址），而非由 `H(file)` 直接决定的输出地址；
