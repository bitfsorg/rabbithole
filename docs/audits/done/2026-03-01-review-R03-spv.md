## Findings

### CRITICAL

无。

### HIGH

无。

（注: 分析了 `VerifyPoW` 的字节序是否正确 — 确认 `DoubleHash` 返回大端序 256-bit 数，`CompactToTarget` 也产生大端序 32 字节 target，字节逐位比较等价于 `hash_as_uint256 <= target_as_uint256`。创世区块测试确认。）

### MEDIUM

**M-1: `ValidateDifficultyTransition` 对零 target 静默通过**

`header.go` L273-275: 当 `prevTarget` 或 `currTarget` 的 `Sign() <= 0` 时返回 nil（成功）而非错误。攻击者可插入 `nBits=0x1d000000`（零 mantissa）的 header，跳过难度转换检查。

实际影响低：`VerifyPoW` 会单独拒绝零 target header，且 `VerifyHeaderChainWithWork` 先调用 `VerifyPoW`。但独立调用 `ValidateDifficultyTransition` 存在此缺口。

**建议**: 零 target 时返回 `ErrDifficultyChange` 错误。

**M-2: `VerifyTransaction` 不检查最低难度 — API 设计陷阱**

`verify.go` L33-92: 只检查 PoW（hash <= target）不检查 target 是否满足网络最低难度。regtest 难度的 header 会通过验证。只有 `VerifyTransactionWithNetwork` 才加最低难度检查。

**建议**: 废弃 `VerifyTransaction`，统一使用 `VerifyTransactionWithNetwork`，或为 `VerifyTransaction` 添加 `Network` 参数。

**M-3: `VerifyHeaderChain` 同样不检查最低难度和难度转换**

`header.go` L372-420: 与 M-2 相同模式。简单 API 缺少关键安全检查。

**建议**: 同 M-2。

**M-4: `CompactToTarget` 不验证指数边界**

`header.go` L85-112: `exponent > 34` 时 `pos = 32 - exponent` 为负，边界检查安全返回全零 target，但静默产生零 target 可与 M-1 交互。

**建议**: 记录为什么 exponent > 34 退化，或添加警告注释。

**M-5: `MemHeaderStore` 高度冲突静默覆盖**

`store.go` L89-90: 同一高度不同 hash 的 header，`byHeight` 被覆盖但 `byHash` 保留两者。`GetHeaderByHeight` 返回最后存储的 header，不处理分叉。

**建议**: 文档化此行为。用于测试可接受，生产需要分叉处理。

### LOW

**L-1: `VerifyTransactionWithNetwork` 覆盖率 67.7%**: 低于 `VerifyTransaction` 的 93.1%。需补充负向测试。

**L-2: header chain 验证不检查时间戳**: Bitcoin 要求块时间戳 > 前 11 块中位数且不超前 2 小时。spec 未要求，但应文档化省略决定。

**L-3: `BoltStore` 使用 gob 编码**: Go 特有，未来 libbitfs-ts 无法兼容。低优先级。

**L-4: `MemTxStore.DeleteTx` O(n*m) 扫描 pubkey 索引**: 可添加反向索引，当前使用模式下可接受。

**L-5: `BuildMerkleTree` 命名/文档误导**: 文档说 "returns all tree levels" 但实际只返回 root。应重命名为 `ComputeMerkleRootFromHashes` 或修改文档。

### SUGGESTIONS

**S-1.** 用 `bytes.Equal` 替代手动字节比较循环（`header.go` L341-345, L407-411; `merkle.go` L70-74）。

**S-2.** `VerifyPoW` 可改用 `math/big` 比较以提高清晰度，性能差异可忽略。

**S-3.** 为 `CompactToTarget` 和 `DeserializeHeader` 添加 fuzz 测试（处理不可信网络输入）。

## Summary

`spv` 包状态良好。所有三个之前识别的 P0/CRITICAL/HIGH 问题（空证明、缺失 PoW、缺失难度检查）已确认修复并有测试覆盖。代码通过创世区块验证、并发安全、良好文档化。

最值得关注的是**双 API 安全陷阱**（M-2/M-3）：简单验证函数缺少最低难度检查，不适合 mainnet 生产使用。这是设计层面的问题而非 bug — 函数按文档工作 — 但两个 API 中一个隐性较弱的设计邀请误用。

无 CRITICAL 或 HIGH 发现。5 个 MEDIUM 是深度防御改进。主网部署前应合并双 API 并添加时间戳验证。
